# Cloud

The Cloudflare Workers cloud (ADR 0004): a Worker in TypeScript with a D1 database. It serves data that is the same for every Viewer, and keeps an email address for each Account (below). Provider logins, stream URLs and Provider requests never come here (ADR 0001).

Deployed at `https://better-iptv-cloud.victor-trinh.workers.dev`; the app's `cloudUrl` (in `gradle.properties`) points there.

## API

Every endpoint but registration needs `Authorization: Bearer <device token>`, and answers `401` without a token a device was given.

- `POST /v1/devices` registers a device: `201 {"token": "…"}`. The app does this on first use and keeps the token in its database. The cloud keeps only the token's SHA-256.
- The metadata, match, search, upcoming, season and charts endpoints TMDB answered (`/v1/metadata`, `/v1/match`, `/v1/search`, `/v1/upcoming`, `/v1/season`, `/v1/charts`) are gone with their tables (#481, ADR 0014): the cloud keeps no TMDB data and holds no TMDB key, as TMDB's terms ask when use ends. They answer `404` like any path the cloud doesn't serve. An app from before #480 that still calls them shows what it kept, or goes without (see #481's PR).
- `POST /v1/subtitles` takes `{"kind": "movie", "tmdbId": 238, "season": null, "episode": null, "languages": ["fr"]}` (a Show's Episode gives its season and episode), 1 to 5 ISO 639-1 languages, and answers `{"subtitles": [{"id": "…", "language": "fr", "source": "opensubtitles", "release": "The.Godfather.1972.BluRay", "hearingImpaired": false, "downloads": 900}], "unavailable": []}`: the best 5 offers per language from OpenSubtitles and Subdl, searched by the Title number and, when the Title facts below hold one, IMDb ID. OpenSubtitles' most downloaded come first, then Subdl's, and those for the hard of hearing after the rest; machine-translated ones are left out. `unavailable` names a service that couldn't answer. Searches are cached per Movie or Episode and language for a week (a day when nothing was found), but not while a service is down. `POST /v1/subtitles/download` takes `{"id": "…"}` from a search and answers `{"format": "srt", "text": "…"}` in UTF-8 (`srt`, `vtt` or `ass`; Subdl's zip is unpacked, and a season's zip gives the Episode's file), `404` when the service no longer has it, `503` when it can't give it now (OpenSubtitles' 20 downloads a day are used up). Every downloaded file is kept, so it is downloaded from a service only once. See `src/subtitles.ts`.
- `POST /v1/title-facts` takes `{"titles": [{"kind": "movie", "tmdbId": 238}]}`, at most 300 Title numbers (kind and the Provider's TMDB number; a 301st is refused), and answers what Wikidata knows of each (#476, ADR 0014): `{"titles": [{"kind": "movie", "tmdbId": 238, "originalLanguage": "en", "imdbId": "tt0068646", "enwiki": "The Godfather", "frwiki": "Le Parrain"}], "notFound": [{"kind": "movie", "tmdbId": 999}], "unavailable": []}`. `originalLanguage` is a primary subtag (P364 through its ISO 639-1 code P218), `imdbId` Wikidata's (P345), `enwiki` and `frwiki` the English and French Wikipedia article names as Wikipedia shows them (the pageviews API writes them with underscores), each null when the item lacks it; `notFound` names the Titles Wikidata has no item for, `unavailable` the ones it couldn't answer for right now, which the device asks again. The Titles not cached are asked of the Wikidata Query Service in one SPARQL query per request, by the TMDB movie (P4947) and show (P4983) ID properties, as `scripts/survey_wikidata.py` does, with a User-Agent naming this repo. Every answer is cached in `title_facts` for good, "no item" included, so a Title asked by any Viewer of any Provider costs Wikidata one query ever, up to 25,000 Titles a day (`FACTS_CACHED_A_DAY`, counted in `facts_cached`: a first Sync of a 58k-Title catalog once spent 130k of D1's 100k daily row writes in an hour; past the budget the answers are still given, just not kept until another day); while Wikidata fails or is slow (25 s), the cached Titles are answered and the rest come back `unavailable`, cached as nothing. Wikidata's data is CC0. A device asks after a Sync, in batches, for every Title number it has no answer for. See `src/title-facts.ts`.
- `POST /v1/file-reads/lookup` takes `{"provider": "<SHA-256 of the Provider's host>", "listings": [123]}`, at most 50 movie Listing ids, and answers `{"files": [{"listingId": 123, "file": {…}}]}`: what a device Header read or played of those Listings' files (audio and subtitle Tracks, picture size, HDR format, bitrate), shared by every Viewer of that Provider. `POST /v1/file-reads` takes `{"provider": "…", "files": [{"listingId": 123, "file": {…}, "prefix": "SC", "hints": ["MULTI-SUBS"]}]}` and keeps them, `204`: each read carries the Listing's Prefix (a code such as `EN` or `4K-FR`, `null` when the name has none; a name is refused) and the Category hints that matched, from Header reads and Playback alike, on every device. The cloud only ever sees the host's hash. See `src/files.ts`.
  - **Learned lines** (ADR 0014, `src/learned-lines.ts`). Each report tallies again every Prefix it touches (and the one a Listing had before), over that Prefix's 200 most recent reads, into `learned_line`, one row per attribute. An attribute is learned once 10 reads tell it (all of the Prefix's Listings when the unknown-Prefix report counted fewer) and 90% of them agree (`MIN_READS`, `AGREEMENT`): the language when the reads carry a single audio language and it is the same, **Multi-audio** when most carry two or more, the quality from the picture size (4K from 3200 wide or 1800 high, HD from 1200 or 700, as the device tells it, so a scope 4K film counts), HDR (Dolby Vision, or HDR10 when the reads mix the two) and Dolby audio from what the files state. Sources, Clutter, Tier tags, the Event time zone and country aliases are never learned. A line that drops under the bar is withdrawn (`withdrawn_at`); a Prefix whose reads split keeps none, and its row (`status = 'split'`, `shares` counting each value) stays for the weekly issue.
- `POST /v1/unknown-prefixes` takes `{"provider": "<SHA-256 of the Provider's host>", "prefixes": [{"prefix": "BR", "listingCount": 260, "example": "BR - Cold Pursuit (2019)"}], "tierTags": [{"word": "PLUS", "listingCount": 40, "example": "PLUS: TNT SPORT 1 HD"}]}`, at most 200 Prefixes and 50 Tier tags (`tierTags` optional), and keeps them with when each was first and last seen, `204`. A device sends these after a Sync finds Prefixes its Prefix table doesn't know, or **candidate Tier tags** (#439): a word before the colon at the start of live Listings' names whose removal makes them the same Channel as another live Listing, Event channels left out, with how many Listings it merges (`tier_tag_candidate`). Candidates are never served or applied: a wrong Tier tag merges two Channels. The Viewer never sees any of it. See `src/prefixes.ts`.
- **The weekly issue.** The `unknown-prefixes` workflow (Mondays) keeps one GitHub issue, "Unknown Prefixes", with a section per Provider hash listing, each only when there is something to show: the unknown Prefixes seen in the last 30 days, the Prefixes whose reads split (`learned_line.status = 'split'`, language and quality, with each value's share and the read count), the learned lines that contradict the Base table, and the candidate Tier tags seen in the last 30 days. A Prefix with a line in the Provider's hand file, and a word already a Tier tag there or in Base, is left out, so a hand line takes it off the next week; with nothing left the issue is closed. `scripts/weekly-issue.mjs` builds the body from the queries' JSON, the Base table and the hand files (tested in `test/weekly-issue.test.ts`).
- `POST /v1/provider-table` takes `{"provider": "<SHA-256 of the Provider's host>"}` and answers that Provider's Provider table (ADR 0014) as `text/plain` in the Base table's format (the header of `core/src/main/resources/dev/betteriptv/core/prefix-table.txt` documents it), or an empty body for a Provider the cloud has never seen. It holds the Provider's hand lines, then its learned lines under `[learned prefixes]` (`XQ | language=pt; quality=4K`, `NF | multi-audio`); a device reads a learned line over the Base table's line for the Prefix, attribute by attribute, and ignores it where a hand line names the Prefix. A device asks at the start of every Sync and describes the Listings it lands with Base plus the answer; without an answer it keeps the last table it got. See `src/provider-tables.ts`.
- `POST /v1/trending` takes `{"language": "fr"}`, the App language, and answers Trending's feed (#477): `{"wikis": [{"wiki": "en", "days": [{"day": "2026-11-06", "articles": [{"name": "Jailer 3", "views": 812345}]}]}, {"wiki": "fr", "days": […]}]}`, English Wikipedia's and the language's most viewed articles of each of the last seven days kept, newest first, named as Wikipedia shows them. The device sums the week and matches the names to its Titles' Wikipedia article names (the Title facts). It reads only D1: the same Cron Trigger reads the Wikimedia pageviews API's daily top 1,000 articles (CC0, no key, a User-Agent naming the app) once per day per wanted wiki, English and each language a device asked in during the last 30 days, after the Games' part and out of the run's budget (`SUBREQUESTS`, 40); it keeps seven days and drops older ones. A day not published yet (the API's 404, some hours after midnight UTC) is asked again an hour later. The Cron Trigger is `triggers.crons` in `wrangler.jsonc`, each minute; run it by hand under `npm run dev` with `curl "http://localhost:8787/cdn-cgi/local/scheduled"`. See `src/trending.ts`.
- `POST /v1/games` takes `{"leagues": ["nhl", "premier-league"]}`, the Leagues a device has on (the ids in `src/schedule.ts`), and answers each League's Games for today and the next seven days: `{"leagues": [{"league": "nhl", "games": [{"id": "401892633", "league": "nhl", "start": "2026-11-04T00:00:00.000Z", "state": "upcoming", "home": {"id": "21", "name": "Toronto Maple Leafs", "shortName": "Maple Leafs", "abbreviation": "TOR", "aliases": ["Toronto Maple Leafs", "Maple Leafs", "TOR", "Toronto"], "logo": "https://…/tor.png", "color": "00205b", "alternateColor": "ffffff"}, "away": {…}, "broadcasters": ["ESPN+"]}]}]}`, by start. A team's `color` and `alternateColor` are ESPN's, six lowercase hex digits with no `#`, each left out when ESPN gives none (#349). `state` is `upcoming`, `live` or `over`; `broadcasters` names the national Broadcasters the schedule knows (US-market: Fox, CBS, ESPN+, Apple TV, never TSN). Never a score or a period. It reads only D1: the same Cron Trigger reads each League's schedule source (`src/schedule.ts`, ESPN's public scoreboard API for every League in M3, `src/espn.ts`, with no user agent since ESPN refuses a browser-like one) while some device asked for the League in the last 2 days (a device asks every 2 minutes while it shows Games), each of its days hourly, and every 5 minutes while the day holds a Game on or starting within 15 minutes, so Live flips within minutes and a quiet day costs little (`dueAt`), 17 requests a run at most (`GAMES_SUBREQUESTS`) out of the run's budget, each day saved as it is read. Each read costs D1 two row writes (the day's `tried_at` before, the day after): the free plan allows 100k a day, and the cron once spent three quarters of it. A League asked for the first time is absent until the next run; one read with no Games this week has `[]`; while ESPN can't answer, the kept copy stands. Games that started over a day ago are dropped (ESPN's CFL endpoint answers out of season with a 2022 game). See `src/games.ts`.

Registration is open: a token identifies a device, so it can be revoked, but it doesn't stop someone from registering one. Registrations and sign-in codes are rate-limited per IP by a Cloudflare rule (Accounts, below).

## Accounts

A TV signs in to an Account from a phone, with no password (ADR 0015). The device token stays the credential: signing in binds it to the Account (`device.account_id`, `device.signed_in_at`), so every endpoint keeps answering the same token, and a device that never signs in is as before. See `src/accounts.ts` and `src/page.ts`.

- `POST /v1/sign-in` answers a fresh Sign-in code for the device, `{"code": "K7M2QX", "url": "https://zugig.app/sign-in?code=K7M2QX", "expiresIn": 600}`: 6 digits and capitals without 0, O, 1 and I, for 10 minutes, replacing the device's previous code. The TV shows the code and a QR of `url`.
  It may carry `{"model": "Fire TV Stick 4K Max"}`, kept to one line of at most 60 characters: the only time a device names its model, which the device list shows (`device.model`).
- `POST /v1/account` answers `{"email": "…"}`, the Account the device is signed in to, or `{"email": null}`. The TV polls it every 2 s while it shows the code.
- `POST /v1/account/devices` answers the devices signed in to this one's Account, by sign-in, `{"devices": [{"id": "3f9a0c1d2e4b5a69", "model": "Fire TV Stick 4K Max", "signedInAt": "2026-11-03T20:00:00.000Z", "thisDevice": true}]}`, or `[]` when it is signed in to none. The id is derived from the token's hash, from which it can't be turned back (#434).
- `POST /v1/account/sign-out`, with `{}` for this device or `{"device": "3f9a…"}` for another on its Account, clears that device's link (account, sign-in date and model), `204`; `404` when no such device is on the Account. The token stays registered.
- Every `/v1/` answer to a registered device carries `Zugig-Account: signed-in` or `none`, so a device signed out from another TV, or whose Account was deleted, goes anonymous at its next request, whatever it asked.
- `GET /sign-in` is the page the QR opens (the code filled in from `?code=`): the code, an email, a "Send me a link" button and the privacy note. No script, nothing loaded from elsewhere. `POST /sign-in` emails a magic link to the address when the code is live. Each IP may type 5 wrong codes in 10 minutes; the sixth try is refused, right or wrong, until they age out (kept by a hash of the IP). A code sends at most 5 links.
- The magic link, `GET /sign-in/link?token=…`, works once, for 15 minutes (even after its code expired). It opens a page with one "Sign in the TV" button, `POST /sign-in/link`, so a mail scanner that opens links (Outlook's Safe Links does) signs nobody in. The button binds the TV to the email's Account, creating it when the email is new. A used, unknown or expired link gets a plain message.
- "Delete my account", linked from the sign-in page: `GET /delete-account` asks for the address, and `POST /delete-account` emails a delete link when an Account uses it, answering the same when none does (and emailing nobody), so the page can't tell who has an Account. Each IP may ask 5 times and each address be sent 3 links in 15 minutes (`delete_request`, by hashes). The link, `GET /delete-account/link?token=…`, works once, for 15 minutes, and opens a page with one "Delete my account" button, `POST /delete-account/link`, which deletes the Account and everything it owns and unbinds every device signed in to it.
- "Reset the Household PIN" (#440), linked from the sign-in page beside it, works as "Delete my account" does, under `/reset-pin` and `/reset-pin/link`, sharing its limits and its table (`delete_link.purpose` is `reset-pin`). Its button clears the Account's Household PIN (a `household` entry `pin` with a null value, stamped with the cloud's time); every TV forgets the PIN at its next pull, and the next one leaving a Kids profile asks for a new one.
- The cloud keeps the email address (`account`), each signed-in device's model, the live codes, and only SHA-256 hashes of the magic tokens (`magic_link`, `delete_link`), of the IPs that typed wrong codes (`sign_in_miss`) and of who asked for delete links (`delete_request`). The Provider login never comes here.

### Account sync

Where a Viewer stopped and what they Watched (#435), and everything else a Profile owns, with the Profiles themselves (#440), follow them between the Account's TVs. See `src/sync.ts`.

- `POST /v1/sync` takes `{"cursor": 0, "provider": "<SHA-256 of the Provider's host>", "current": "0123456789abcdef", "progress": [{"profile": "0123456789abcdef", "title": "show/1399", "season": 1, "episode": 2, "position": 600000, "duration": 3600000, "watched": false, "removed": false, "at": 1762500000000}], "entries": [{"kind": "favourite", "profile": "0123456789abcdef", "key": "tsn 1", "value": "1", "at": 1762500000000}]}`, at most 500 changes and 500 entries, and answers `{"cursor": 42, "reset": false, "progress": […], "entries": […]}`: the Account's changes stamped after the cursor, in the same shape, the device's own included. `403` when the device isn't signed in, which the device takes as signed out. A change without a `profile` (an app from before #440) is refused, `400`.
- A Profile is named by the id its device made for it, 16 hex digits, the same on every TV once it syncs; `current` is the one the device is on, kept per device (`device.profile`).
- `entries` are the rest, one row per thing (`synced`), the latest `at` winning as for progress, `value` null for a removal: `profile` (the Profile itself, `key` empty, `value` `{"name": "Sam", "kids": false}` as JSON, null once deleted), `favourite` (`key` a Channel key) and `not_this_game` (`key` the Game key, `|`, the Channel key), kept per Provider; `setting` (a Profile's Content languages, Prefer original audio, App language, Play next automatically, Leagues and remembered tracks, by name) and `title_choices` (`key` a Title key, per Provider when it is a Listing's); and `household` (no Profile; `region`, or `pin`, the Household PIN's salted hash, never its digits). A deleted Profile's rows go with it, and what an offline TV pushes for it later is dropped. The device's own settings (Quality cap, Text size, subtitle style, Background reading) are never sent.
- A change is a Movie's (`season` and `episode` null) or an Episode's position, duration, Watched, or `removed` ("Remove from Continue watching", a tombstone), at `at` by the device's clock, held to the cloud's so a clock that runs ahead can't win every change after it. Per Movie or Episode the latest `at` wins, whichever arrives first, so of two TVs watching one Title the last to stop wins.
- `title` is the device's Title key. By TMDB ID (`movie/238`, `show/1399`) it is the same on every Provider; by Listing (`movie/listing/123`, an Unmatched Title or a Sports replay) it is kept under `provider` and only answered to a device on that Provider.
- The cursor is the Account's sync sequence number (`account.sync_seq`), bumped once per push and stamped on every row it changes, so a device offline for a week gets everything since its cursor. Tombstones are dropped 30 days after `at`; a device whose cursor is older than a dropped tombstone gets everything the Account has, marked `reset`, and forgets the history it pulled before that isn't in it. A device that just signed in asks from `0` and merges.
- Entries are stamped from the same sequence, so one cursor covers them; their removals are kept (they are few), so only progress tombstones cause a `reset`.
- The first sync after signing in merges the device into the Account: it pulls from `0`, gives each of its Profiles the Account's of the same name (a Kids one merging into one that isn't stays Kids), keeps the rest as new, and pushes all of its data; past 5 Profiles the TV first asks which to keep. Migration `0018_account_sync.sql` dropped #435's progress rows, which named no Profile: each signed-in device pushes its history again at its first sync with #440.
- The device pushes after each stop or change and syncs on launch and on coming to the front; what it pulls lands between screens. Signing out takes the Account's data off the device, leaving one blank Profile. A device that never signs in never calls it.

### Setting up the domain and the sender

The QR must point at the app's own domain, not `workers.dev`, which on a TV reads as phishing.

1. **Domain.** Add the domain (say `zugig.app`) to Cloudflare, then attach it to the Worker: Workers & Pages → `better-iptv-cloud` → Settings → Domains & Routes → Add → Custom domain → `zugig.app`. Then set `SITE_URL` (`https://zugig.app`) and `EMAIL_FROM` (`Zugig <sign-in@zugig.app>`) under `vars` in `wrangler.jsonc`. Until `SITE_URL` is set, the QR and the links name whatever address the request came to.
2. **Sender.** In Resend (free tier: 3,000 emails a month, 100 a day), Domains → Add domain → `zugig.app`. Resend lists the DNS records to add in Cloudflare's DNS, all DNS-only (grey cloud):
   - `TXT resend._domainkey` with the DKIM key Resend shows,
   - `MX send` → `feedback-smtp.<region>.amazonses.com`, priority 10 (the bounce path),
   - `TXT send` → `v=spf1 include:amazonses.com ~all` (SPF for the bounce path),
   - and, recommended, `TXT _dmarc` → `v=DMARC1; p=none;`.

   Once Resend says Verified, create an API key with Sending access for that domain and set it with `npx wrangler secret put RESEND_API_KEY`. Without it no email goes out, and the page says it couldn't send one.
3. **Rate limit.** Security → WAF → Rate limiting rules → Create rule, on the domain's zone (and on the `workers.dev` route turned off, Settings → Domains & Routes, so the rule can't be walked around):
   - If incoming requests match: `(http.request.method eq "POST" and http.request.uri.path in {"/v1/devices" "/v1/sign-in" "/sign-in" "/delete-account"})`
   - With the same characteristics: IP
   - When rate exceeds: 10 requests per 10 seconds (the free plan's period), then Block for 10 seconds.

   A TV asks one code per 10 minutes and a phone sends a link or two, so no household meets it; a script registering devices or guessing codes does. The per-IP wrong-code count above is the Worker's own second line.

Point the app at the domain by changing `cloudUrl` in `gradle.properties` once it serves the API.

## Secrets

- `OPENSUBTITLES_API_KEY`, `OPENSUBTITLES_USERNAME`, `OPENSUBTITLES_PASSWORD`: an API consumer's key (opensubtitles.com → API consumers) and the free account its downloads count against; downloads without a login are capped per IP, and the Worker's IPs are shared. Without them, OpenSubtitles isn't asked.
- `SUBDL_API_KEY`: from subdl.com → account → API. Without it, Subdl isn't asked.
- `RESEND_API_KEY`: a Resend API key with Sending access for the app's domain (Accounts, above). Without it, no sign-in email goes out.

## Develop

```sh
npm install
npm test          # seam 2: the API in the Workers runtime (Miniflare), with ESPN, Wikidata, Wikipedia, the subtitle services and the email sender faked

npm run dev       # a local Worker on :8787; put the subtitle secrets and RESEND_API_KEY in .dev.vars
```

Point a debug build at a local Worker with `./gradlew assembleDebug -PcloudUrl=http://<this Mac's IP>:8787`.

## Deploy

CI (`.github/workflows/cloud.yml`) tests every change under `cloud/`, and on `main` applies D1 migrations and deploys. It needs two repository secrets:

- `CLOUDFLARE_API_TOKEN`: a Cloudflare API token from the "Edit Cloudflare Workers" template, with D1 edit added.
- `CLOUDFLARE_ACCOUNT_ID`: the account ID `npx wrangler whoami` shows.

To deploy by hand: `npm run deploy`. Schema changes go in a new file under `migrations/`.

Once `0023_drop_tmdb.sql` has deployed (#481), delete the TMDB key from the Worker, which no code reads any more: `npx wrangler secret delete TMDB_TOKEN` (or Workers & Pages → `better-iptv-cloud` → Settings → Variables and Secrets), and revoke it on themoviedb.org → Settings → API. Take `TMDB_TOKEN` out of any local `.dev.vars` too.

### Provider tables

Hand lines live in `provider-tables/`, one file per Provider named `<SHA-256 of its host, lowercase hex>.txt`, in the Base table's format; no Provider's host is written anywhere. `npm run deploy` (and so CI's deploy) loads them into D1's `provider_table` after the migrations, with `scripts/provider-tables.mjs`: each file's row is replaced in place, then the rows of files no longer in the repo are deleted, so a device asking mid-deploy never gets an empty table for a file that stays. `npm run provider-tables` loads them into a local Worker's D1 (`npm run dev`). Devices pick a change up at their next Sync. The Gradle tests check that every file parses as a Provider table, and the app still ships them as the table a device uses until the cloud has answered once.
